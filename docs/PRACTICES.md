# Practices behind the dotagent and this workflow

Old engineering habits and newer agent habits in this era, side by side. Each row says where the idea comes
from and where the dotagent uses it. Figures marked "reported" came from secondary write-ups.

| Practice | Where it comes from | In the dotagent |
|---|---|---|
| Small, self-contained changes, tests with the code, refactors apart from features | [Google engineering practices: small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html) | One subtask is one commit. A PR stays reviewable, a few hundred changed lines is typical. A refactor is its own subtask. |
| Review works best on small changes, so keep each PR small | [Google, Modern Code Review: A Case Study at Google](https://research.google/pubs/modern-code-review-a-case-study-at-google/) (ICSE-SEIP 2018: interviews, a survey, and 9 million reviewed changes). The 400 line figure is our choice, not the paper's. | The 3 to 8 subtask range per PR. It is a range, a bigger task becomes more PRs. |
| One logical change per commit, `type(scope): summary` | [Conventional Commits](https://www.conventionalcommits.org) and plain atomic commit practice | The commit hook requires a scope and one line. A git hook gives humans the same rule. |
| Low coupling, high cohesion: a small public interface, one way dependencies, shared code in a shared library, boundaries checked in CI | [Shopify, Enforcing Modularity in Rails Apps with Packwerk](https://shopify.engineering/enforcing-modularity-rails-apps-packwerk): a modular monolith whose packages may depend only on declared packages and use only each other's public constants, checked in CI. | `ARCHITECTURE.md` records the style, the coupling rule, and each module's interface. A boundary check in CI enforces it, and setup greps the code to list today's violations. |
| Domains with clear layers and gateways at scale | [Uber, domain oriented microservice architecture](https://www.uber.com/en/blog/microservice-architecture/) | Slices stay inside one module and cross modules only through its interface. |
| Spec first, small chunks, commits as save points, never commit code you cannot explain | [Addy Osmani, my LLM coding workflow](https://addyosmani.com/blog/ai-coding-workflow/) | The lead plans, builds one commit per subtask, and a reviewer in a fresh context checks the diff. |
| Give the agent a check it can run | [Claude Code best practices](https://code.claude.com/docs/en/best-practices) | Every subtask runs build, lint, test. `/goal` or a Stop hook gates the end. |
| Keep CLAUDE.md short, use hooks for what must always happen | The same best practices page | `AGENTS.md` stays under 60 lines. Commit, PR, merge, dash, and read rules are hooks. |
| Files of one responsibility, most between 100 and 300 lines, rarely past 500 | [ESLint `max-lines`](https://eslint.org/docs/latest/rules/max-lines) (default 300, docs say recommendations usually range from 100 to 500) and Clean Code (about 200 lines typical, 500 at most, "not a hard and fast rule", reported from secondary summaries) | Size is a cohesion signal. A file past about 500 lines gets split by responsibility in its own slice, and the reviewer flags it. |
| One CI trigger per event: the PR gate on `pull_request`, heavier checks on push to the default branch | [GitHub Docs, events that trigger workflows](https://docs.github.com/en/actions/writing-workflows/choosing-when-your-workflow-runs/events-that-trigger-workflows): `push` fires for any pushed branch and `pull_request` for every update of a PR, so listing both runs the same checks twice. The split follows a real Go backend's PR and staging workflows. | `ci-pr.yml` and `ci-default.yml`. A plain commit on a branch starts nothing. |
| Deterministic steps around the agent loop, at most 2 CI rounds | [Stripe Minions](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents) | Git, the gate, and CI are fixed steps, and a fix gets two tries from the lead, then the run stops. |
| Scale effort to the task, avoid spawning too many agents | [Anthropic, multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) | One sentence diffs have no plan. Everything else is one loop with at most a reviewer and `Explore` spawned, each with an objective, an output shape, and boundaries. |
| Writing agents share one thread, parallel writers collide | [Cognition, do not build multi-agents](https://cognition.ai/blog/dont-build-multi-agents), and Anthropic's note that coding has fewer parallel pieces | The lead builds subtasks one at a time in one context, so no two writers make conflicting choices. A reviewer only reads. |
| Keep context small and high signal: just in time reads, minimal tools, focused agents | [Anthropic, Effective context engineering for AI agents](https://anthropic.com/engineering/effective-context-engineering-for-ai-agents) | The ship skill is one prompt, the reviewer gets a small brief, and the lead reads ranges, not whole files. |
| Enforce routing with hooks, keep edits with the main model | [Spotify Portal, token usage cut](https://engineering.atspotify.com/2026/9/portal-by-spotify-cut-my-claude-code-token-usage-by-90) | The read hook blocks whole reads over 500 lines. The lead edits, it does not delegate edits. |
| Trust but verify with a second pair of eyes | Code review as an old habit, a fresh context reviewer as the new one | The reviewer sees the diff and the plan, never the author's reasoning. |
| One agent with progressive disclosure beats a pile of subagents: shared context, fewer lossy handoffs, hard limits in tools and hooks, fold one at a time and keep what holds up | [Anthropic, when to fold subagents into your main agent loop](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop) | One loop for every task, one subagent (the reviewer, a black box verifier) and `Explore` for wide reads, hard rules in the guard hook, and the Haiku worker swarm removed. |
| Most multi-agent failures come from design and verification, not the model: step repetition, no termination, incomplete or wrong verification | [Berkeley, Why do multi-agent LLM systems fail](https://arxiv.org/html/2503.13657v3) (14 failure modes in 1,642 traces) | A bounded fix ladder, a fresh reviewer, the gate record, and CI as the final check. |
| A long run needs a written record and a startup check, and agents must not edit or drop tests | [Anthropic, effective harnesses for long running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) | `docs/TODO.md` and git are the record, `continue` runs the gate check before new work, and the reviewer flags a deleted, skipped, or loosened test. |
| Share full context, not summaries, between agents that act | [Cognition](https://cognition.com/blog/dont-build-multi-agents) | The same agent plans and builds, so nothing is summarized away between them. |
| A task list file in the repo: small tasks, a checkbox per step, the file path in the line, phases or sections in order, tests per section | [spec-kit style tasks.md](https://skills.sh/ahgraber/skills/spec-kit-tasks) as summarized by community skills, and [Addy Osmani](https://addyosmani.com/blog/self-improving-agents/) on tasks small enough for one session with pass or fail criteria | `docs/TODO.md`: one section per PR, one subtask per commit with its size, message, detail, and verify. Ignored by git and replaced per task, so it is a report and not history |
| Plan before code, review the plan, never guess | [Backlog.md talk](https://ai.engineer/talks/backlog-md-terminal-kanban-board-for-managing-tasks-with-ai-agents-alex-gavrilescu-funstage): criteria first, then an implementation plan before any code | The lead reads and writes only the TODO while planning, asks the user with a recommended answer, and the hook enforces read only planning |
| A commit message says what changed, not where it sits in a plan | [Conventional Commits](https://www.conventionalcommits.org) and plain atomic commit practice: history should read as a change log | The hook and the `commit-msg` git hook refuse `milestone-1`, `task-2`, `slice 3`, `wip`, `finishing task`, and `(#N)` (GitHub adds the PR number on merge, only the merge commit subject ends with it, one line, no body, and never a squash) |

## What is a choice, not a rule

- File size has no hard law behind it. The size and defect research I found is mixed: El Emam and
  colleagues showed that class size confounds many metrics, so size alone does not explain
  defects (El Emam and colleagues, IEEE Transactions on Software Engineering, 2001).
  So 100 to 300 lines is a typical range and 500 is a prompt to ask whether the file does two
  things, not a line that fails a build. The only hard number is the 500 line limit on whole
  reads, `READ_LINES` in `hooks/guard.py`, which saves context and does not judge the code.
- The 500 line whole read block is an assumption from a smaller model era: it saves context, and it costs extra reads on a big file. [Anthropic](https://anthropic.com/engineering/managed-agents) found a harness workaround (context resets) went dead weight on a newer model, so re-test this limit when the model changes, and raise or drop it if a run shows more round trips than context saved.
- PR size is a range, 3 to 8 subtasks and a few hundred changed lines, drawn from the review sources above. It is not a limit, the right size depends on the project.
- Sequential subtasks trade speed for safety. Parallel writers need isolated worktrees, which
  the dotagent does not set up yet.
